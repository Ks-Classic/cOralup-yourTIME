# ID統一化リファクタリング

**作成日**: 2025-12-19
**更新日**: 2026-06-29

## 1. 背景と目的

### 問題
現在、システム内で「診断（来院）」を識別するIDが2種類存在している：
- `visit_id` (UUID): データベース主キー
- `session_id` (短いコード): 後方互換用・表示用

これらの役割が曖昧だったため、以下の問題が発生していた：
1. **兄弟のデータ混在**: 同じ親御さんが複数の子供を登録する際、古いsessionIdが新しい子供に引き継がれてしまい、データが上書きされる
2. **API引数の不統一**: APIによって「sessionIdを受け取る」「visitIdを受け取る」「両方受け取る」がバラバラ
3. **外部キー参照の不一致**: テーブルによってsession_idで紐付けたりvisit_idで紐付けたりしている

### 目的
**ID設計を確定し、兄弟登録・レポート再表示・LINE再送でデータが混ざらない状態にする。**

---

## 2. 設計方針

### 確定事項

| ID | 役割 | 用途 |
|---|---|---|
| **`visit_id`** (UUID) | **データベースの主キー・紐付けキー** | すべてのテーブル間リレーション、API内部処理、履歴リンク |
| **`session_id`** | **人間用の表示ID** | QRコード表示、受付番号、デバッグログ、電話サポート時の確認 |

### ルール
1. **新規テーブル・API**: `visit_id` を必須・優先にする。`session_id` は表示/検索補助以外で受け取らない。
2. **既存テーブルのFK**: すべて `visit_id` を優先参照。`session_id` からの参照は非推奨とし、将来的に削除。
3. **session_id の用途を限定**: 
   - `visits.session_id` カラムは残す（表示・検索補助用）
   - 他テーブルの `session_id` カラムは新規レコードでは NULL のまま、`visit_id` を必ず設定
4. **レジューム機能**: LINE User ID + 未完了の visit_id で復元する。session_id は使わない。

## 5. 今後の運用

### 新規機能開発時
- 必ず `visit_id` を外部キーとして使用
- `session_id` は visistsテーブルの表示用カラムとしてのみ参照

### レガシーコード修正時
- session_id 依存を発見したら visit_id 依存に書き換える
- 既存データの session_id は残しておいて問題ない（表示用として活用可能）

---

## 6. 備考

- session_id を完全廃止する必要はない
- 表示用・人間可読性のために残す価値がある
- 重要なのは「データの紐付けは visit_id に統一する」こと

## 6. セキュリティ: admin認証の穴と修正（2026-06-29）

### 6.1 発見（本番で現存していた穴・CRITICAL）

世界一レベルセルフレビューの過程で、`/api/admin/*` の認証が**ルートごとにバラバラ かつ多数が無認証**であることが判明。

| ルート | メソッド | 修正前の状態 |
|---|---|---|
| `schemas` / `schemas/[id]` | GET/POST/PUT/DELETE | fail-open（`if (!bearer && !headerKey) return // 暫定`）→ 未認証でDB削除可 |
| `visits` | GET | fail-open（`!adminApiKey` で許可）→ 個人情報閲覧可 |
| `diagnosis-schema` | POST/GET | **認証皆無** → スキーマ書込可 |
| `ai-prompts` | POST/PATCH | **認証皆無** → プロンプト改ざん可 |
| `paper-recovery/save-questionnaire` | POST | **認証皆無** → 問診データ書込可 |
| `spreadsheet-import/execute` | POST | **認証皆無** → 一括取込可 |
| `paper-recovery/analyze`, `analytics`, `analytics/report`, `realtime-status` 他 | GET/POST | **認証皆無** → データ閲覧・AI課金 |

加えて：
- middleware の `/admin` ページゲートが `ADMIN_PASSWORD` 未設定で **fail-open**（全解放）
- admin認証Cookieが `path:'/admin'` で、ブラウザが `/api/admin/*` にCookieを送れない構造的欠陥（fail-openの温床）

### 6.2 修正（middleware一箇所に集約・fail-closed）

- **`src/middleware.ts`**: 全 `/api/admin/*`（`/api/admin/auth` 除く）を chokepoint でゲート。許可条件＝「admin Cookie / `staff_session` JWT / `ADMIN_API_KEY` のいずれか」。本番でシークレット皆無は 503、認証なしは 401。matcher に `/api/admin/:path*` 追加。`/admin` ページゲートも本番 fail-closed 化。
- **`src/lib/admin-auth.ts`**: admin Cookie の `path` を `/admin`→`/`（`/api/admin/*` に届くように）。`verifyAdminAuth` を本番 fail-closed。
- **`src/app/api/admin/auth/route.ts`**: `ADMIN_PASSWORD` 未設定時、本番は 503。
- 各ルートの既存 passthrough は middleware 背後の defense-in-depth として残置（変更なし）。
- 全 `/api/admin/*` 呼び出し元は `/admin/*` 配下ページのみ（公開/parent側ゼロ）と確認済み → 正規フロー非破壊。

### 6.3 デプロイ前 必須env（fail-closedの前提）

- [ ] `ADMIN_PASSWORD` を本番(Vercel)に設定（未設定だと admin 全 401/503・ログイン不可）
- [ ] `STAFF_SESSION_SECRET`（>=32字）設定済み確認（staff_session 認可に使用）
- [ ] デプロイ直後、admin Cookie の path 変更で**既存admin/スタッフは再ログインが必要**（同一IDなら過去データと統合可）

### 6.4 セキュリティレビュー(2回目)結果と対応

security-reviewer の独立レビューで判明し対応済み：

- **C-1（CRITICAL・新規作り込み）**: middleware の staff session 判定が `role` の存在のみ検証 → 任意のスタッフJWT(role:'staff')で admin API に昇格可能だった。`payload.role === 'admin'` に修正。
- **H-2（HIGH）**: `/api/admin/auth` 除外が `startsWith` で将来の `/api/admin/authorize` 等を巻き込みバイパスの恐れ → 完全一致＋`/`配下に限定。
- **H-1（HIGH・暫定対応）**: admin ログインにレート制限なし。方針：**覚えやすいパスフレーズ運用 + 失敗時固定遅延(800ms)のストッパー**で当面凌ぐ。恒久対策(Upstash等のIP単位レート制限/ロックアウト)は次スプリント。
  - 運用注意: ADMIN_PASSWORD は「4桁PINや単語1個」ではなく**覚えやすい3語フレーズ**推奨（例: `sakura-coral-2026`）。遅延と併せ現実的に総当たり不能。

### 6.5 残課題（次スプリント）

- [ ] **H-1 恒久**: Upstash 等で `/api/admin/auth` に IP単位レート制限/ロックアウト（現状は失敗遅延800msの暫定ストッパーのみ）
- [ ] **M-1**: admin Cookie値 `base64(password)` は可逆 → Web Crypto HMAC(`STAFF_SESSION_SECRET`流用)化し、Cookie窃取時の平文露出を防ぐ
- [ ] H-1(LINE認証): staff session JWT を URL `?token=` で渡す方式を、サーバ発行の短命ワンタイムコード交換に置換（現状は `replaceState` で履歴消去の緩和のみ）
- [ ] H-3: `/api/line/send-demo-report` に staffId 単位の rate-limit（LINE課金保護）
- [ ] REF-2: admin Cookie 比較を定数時間比較化（タイミング攻撃緩和）

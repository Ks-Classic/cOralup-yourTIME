# スキーマエディタ仕様書

## 概要

管理者がスタッフの診断項目と親御さんの問診票項目を、管理画面から自由に編集・追加・削除できる機能。

---

## 1. アーキテクチャ

### データフロー

```
┌─────────────────────────────────────────────────────────────┐
│                    form_schemas テーブル                     │
│  - schema_id: 'preschooler_v1' / 'elementary_v1' / 'diagnosis_v1'
│  - form_type: 'questionnaire' / 'diagnosis'                  │
│  - config: JSONB (FormSchemaConfig)                          │
│  - is_active: boolean                                        │
└─────────────────────────────────────────────────────────────┘
                              ↑
             CRUD via Server API (Supabase Service Role; RLS ON)
                              ↑
┌─────────────────────────────────────────────────────────────┐
│              /admin/schema-editor (管理画面)                 │
│  - 問診票スキーマ編集                                        │
│  - 診断項目スキーマ編集                                      │
│  - リアルタイムプレビュー                                    │
│  - バージョン管理                                            │
└─────────────────────────────────────────────────────────────┘
                              ↓
                    読み込み (useFormSchema hook -> /api/admin/schemas経由)
                              ↓
┌─────────────────────────────────────────────────────────────┐
│           問診票入力画面 / 診断入力画面                      │
│  - DBからスキーマを取得                                      │
│  - 動的にフォームをレンダリング                              │
└─────────────────────────────────────────────────────────────┘
```

---

## 2. データベース設計

### RLS/アクセス方針
- 全publicテーブルはRLS ON。service_roleのみ全操作許可。
- クライアントはSupabase直呼び出し禁止。/api/admin/schemas などサーバーAPI経由でCRUDし、Next側で認可チェックする。
- 管理UIのみ `ADMIN_API_KEY`（Bearer or x-admin-key）で保護。実際の問診・診断・LINE連携など本番フローはサーバー側でService Roleを使い、クライアントはキー不要。

### 既存テーブルの活用

`form_schemas` テーブル（既存）を使用:

```sql
-- 既存テーブル構造
CREATE TABLE form_schemas (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  schema_id VARCHAR(50) UNIQUE NOT NULL,
  event_id UUID REFERENCES events(id),
  form_type VARCHAR(20) NOT NULL,  -- 'questionnaire' | 'diagnosis'
  name VARCHAR(200) NOT NULL,
  description TEXT,
  version VARCHAR(20) NOT NULL DEFAULT '1.0',
  is_active BOOLEAN DEFAULT true,
  config JSONB NOT NULL,  -- FormSchemaConfig
  created_by UUID REFERENCES auth.users(id),
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

### スキーマ種別

| schema_id | form_type | 説明 |
|-----------|-----------|------|
| `preschooler_v1` | questionnaire | 未就学児用問診票 |
| `elementary_v1` | questionnaire | 小学生以上用問診票 |
| `diagnosis_v1` | diagnosis | スタッフ診断評価項目 |

## 4. 管理画面UI設計

### ページ構成

```
/admin/schema-editor
  ├── タブ: 問診票 | 診断項目
  ├── サブタブ: 未就学児 | 小学生以上 （問診票の場合）
  │
  ├── 左ペイン: 編集エリア
  │   ├── セクション/カテゴリ一覧（ドラッグ&ドロップ）
  │   ├── 項目編集フォーム
  │   └── 追加/削除ボタン
  │
  └── 右ペイン: リアルタイムプレビュー
      ├── デバイス切替（モバイル/タブレット/PC）
      └── 実際のフォーム表示
```

### 編集機能（現状）

#### 問診票編集
- [x] セクションの追加/削除（UI上）・タイトルのインライン編集
- [x] 項目の追加/削除（UI上）・名称編集・タイプ変更
- [x] ラジオ/チェック/セレクトの選択肢編集（追加/削除/ラベル変更、自動初期化あり）
- [x] 必須/任意の切り替え、プレースホルダー編集
- [ ] 並び替え（ドラッグ&ドロップ）※未実装
- [ ] バリデーション詳細設定（min/max等のUI）※未実装
- メモ: タブ切替時はローカルキャッシュで編集中の状態を保持（API再読込を避ける）

#### 診断項目編集
- [x] カテゴリ/項目の追加・編集（表示/非表示切替含む）
- [x] 回答タイプ変更、選択肢編集
- [ ] 並び替え（カテゴリ/項目のD&D実装中途）

#### 削除の扱い（現状）
- UI削除はデフォルトでローカル除去＋soft delete。保存時に送信されない既存IDは `is_active=false` に自動更新。
- ハード削除: 既存IDに限り「完全削除」操作でリクエストし、保存時にDBから `DELETE`。カテゴリ削除時は先に配下項目を全削除してからカテゴリを削除（FK対策）。
- 保存成功後はキャッシュをクリアし、次回タブ切替でDB再フェッチ。
- 管理画面取得では `is_active` を保持したまま返す（非表示状態を編集可能にするため）。ランタイム配信用 `/api/questionnaire/items` は `is_active=true` のみ返却。
- 選択肢 `options` が文字列として保存されている場合はJSONパースして返す。

## 5. API設計

### エンドポイント

```typescript
// GET /api/admin/schemas
// スキーマ一覧取得

// GET /api/admin/schemas/[schemaId]
// 特定スキーマ取得

// PUT /api/admin/schemas/[schemaId]
// スキーマ更新

// POST /api/admin/schemas
// 新規スキーマ作成

// POST /api/admin/schemas/[schemaId]/versions
// バージョン保存
```

#### データ取得の分岐（問診票）
- 管理画面: `questionnaire_categories` と `questionnaire_items` を `is_active` フィルタ無しで取得し、`isActive` フラグとして返却。
- 親アプリ: `/api/questionnaire/items` で `is_active=true` のカテゴリ・項目のみ返却。カテゴリ `target_age` が `preschool` / `elementary` / `all` で分岐。
- スキーマIDは `preschooler_v1` / `elementary_v1` を共通テーブルで運用（別テーブルは持たず、`target_age` で切り分け）。

#### 削除設計メモ（追加予定）
- リクエスト拡張案: `softDeleteIds`, `hardDeleteIds` をセクション/項目単位で渡す。
- サーバ側:
  - soft: 対象IDを `is_active=false` 更新。非対象で存在していないIDは無視。
  - hard: 対象IDを `DELETE`。基本は管理者明示操作のみで実行。
- 既存挿入/更新ロジックは維持しつつ、欠落IDの扱いを上記ポリシーに合わせる。

## 7. セキュリティ

### アクセス制御
- 管理画面は認証必須
- role: 'admin' または 'staff' のみアクセス可能
- RLS (Row Level Security) で保護

### バリデーション
- スキーマ構造のバリデーション
- 必須項目の削除防止
- 循環参照の検出

---

## 8. 運用フロー

### 項目変更時
1. 管理者が管理画面にアクセス
2. 編集したい項目を選択
3. 変更を加える（リアルタイムプレビューで確認）
4. 「保存」で即座に反映
5. バージョン履歴に自動保存

### ロールバック
1. バージョン履歴から過去バージョンを選択
2. 「このバージョンに戻す」で復元

## 0. この文書で確定すること

この文書は、ガイドページの見た目だけでなく、スタッフ登録、本人ログイン、イベント参加、外部ブラウザ移行、デモ練習、当日操作、トラブル復旧までを一つの体験として定義する。

### 解決する課題

> 8/2 YourTIME.8th 東京に参加する新規・既存スタッフが、運営者の個別説明なしで、自分のスマートフォンを本番利用可能な状態にし、デモによる事前確認まで完了できるようにする。

### 成功の定義

- 新規スタッフは、ガイドだけで実名登録、8/2イベント参加、本人ログイン、ショートカット追加、デモ確認を完了できる
- 既存スタッフは、プロフィールを重複作成せず、8/2イベントへの参加追加と再ログインができる
- 当日に運営者が説明しなくても、QR受付からレポート・案内のLINE送信まで進行できる
- 困ったときは、症状から復旧手順を自分で特定できる
- cOral upのブランドを保ちながら、制作事例として見せられる完成度、速度、アクセシビリティを両立する

### 今回やらないこと

- 8/2前のアプリ全体リファクタリング
- ガイドページからの共通PIN公開
- WebGL、3D、スクロールジャックなど、現場操作を不安定にする演出
- PWAとしてのインストール案内。現状はmanifestとService Workerを持たないため、「ホーム画面にショートカットを追加」と表現する
- スタッフ全員の準備進捗を管理者が集計する機能。ページ内チェックは端末ローカルの自己確認とする

## 2. 対象ユーザーと利用状況

### 2.1 ペルソナ

| ペルソナ | 状況 | 最も重要なゴール | 主な不安 |
|---|---|---|---|
| 初参加スタッフ | スタッフ用LINEもアプリも未登録 | 迷わず準備を完了する | 何をどの順番で行うか分からない |
| 参加経験のあるスタッフ | 過去イベントで一度登録済み | 再登録せず8/2参加状態にする | 鹿児島など以前のイベントが表示される、ログインURLを忘れた |
| セッション切れスタッフ | ホーム画面ショートカットはある | 自力で本人ログインに戻る | PIN画面が出て先へ進めない |
| 当日スタッフ | 会場で来場者を担当 | 操作順を即座に確認する | カメラ、QR、LINE送信で止まる |
| 運営者 | 参加者全体を支援する | 個別説明なしで同じ準備品質に揃える | 誰かの端末だけ当日動かない |

### 2.2 利用コンテキスト

- 事前準備は自宅などで、LINEからスマートフォンで行う
- 当日は立った状態、片手、混雑、4G/5Gまたは会場Wi-Fiを想定する
- ページ閲覧者の中心はスマートフォン。デスクトップは運営者による説明・確認用途
- LINE内ブラウザは認証の入口に使用するが、診断操作はSafariまたはChromeで行う
- 既存スタッフの割合が高いため、ファーストビューで「初めて」と「登録済み」を同格に分岐させる

## 3. ユーザーストーリーと受入基準

### US-01 初めての登録

初参加スタッフとして、説明者がいなくても実名登録とイベント参加を完了したい。

**受入基準**

- 友だち追加ボタンはすべて `https://lin.ee/ZUvmToP` を開く
- 実名を送信する理由と入力例が送信前に分かる
- 「8/2 YourTIME.8th 東京」を選ぶことが明記される
- 5分以内を目安に、ホームで実名とイベントの「登録済み」を確認できる

### US-02 過去に登録済み

既存スタッフとして、プロフィールを作り直さず8/2イベントだけ追加したい。

**受入基準**

- 「再登録は不要」が分岐カードの冒頭で分かる
- LIFF本人ログインからホームへ進める
- 8/2が未登録ならホームの「参加登録」またはLINEの「イベント変更」で追加できる
- 過去のイベント参加を削除せず、同じ人物を `event_staffs` の多対多で管理する
- 2分以内を目安に登録状態を確認できる

### US-03 再ログイン

セッションが切れたスタッフとして、共通PINに頼らず本人ログインへ戻りたい。

**受入基準**

- セッションが最大7日で切れる可能性をFAQで説明する
- `/staff/login` に「LINEで本人ログイン」ボタンがある
- ブックマークからログイン画面になった場合の回復手順を示す
- 共通PINを公開ページに表示しない

### US-04 外部ブラウザ移行

iPhone／Android利用者として、カメラが安定する独自ブラウザでアプリを使いたい。

**受入基準**

- iPhoneはSafari、AndroidはChromeを推奨する
- 自動遷移しない場合に、ユーザーが押せる「Safari／Chromeで開く」回復ボタンがある
- LINE内ブラウザを使い続けない理由を、専門用語なしで説明する
- iPhone SafariとAndroid Chromeの実機で外部遷移を確認する

### US-05 デモ練習

スタッフとして、本番データを汚さず、自分のLINEに届くところまで試したい。

**受入基準**

- デモの問診、分析、レポートはモックであり、本番のvisit、report、LINE送信ログを更新しない
- ログイン中のスタッフ本人にだけ、デモレポート通知と相談案内の2通が届く
- 「保護者には送られない」と開始前に明記する
- デモ完了後にチェックリストを更新できる

### US-06 当日操作

当日スタッフとして、来場者対応の順番と完了状態を迷わず確認したい。

**受入基準**

- 来場者のQR → 問診確認 → 写真・診断 → AI分析 → レポート確認 → LINE送信の順を1画面で把握できる
- 操作に迷ったとき、ページ内ナビから「当日の流れ」「トラブル解決」へ2タップ以内で移動できる
- 8/2の新規visitが正しいイベントIDへ保存される

### 4.0 セルフオンボーディングの基本構造

このページを長い取扱説明書にはしない。入口で利用目的を選び、必要な情報だけを一手順ずつ見せる。

## 5. 正式な操作フロー

### 5.1 初めて登録する人

```text
ガイド
  → スタッフ用LINEを友だち追加
  → 実名（姓名）を送信
  → 「8/2 YourTIME.8th 東京」を選択
  → 届いたスタッフアプリURLを開く
  → LINEで本人認証
  → Safari／Chromeで開く
  → ホームで実名と「登録済み」を確認
  → ホーム画面ショートカットを追加
  → デモを最後まで操作
  → 自分のスタッフLINEに2通届くことを確認
  → 準備完了
```

**ページ上の案内文**

> 初めての方は、スタッフ用LINEへの友だち追加から始めます。LINEの表示名とは別に、現場で確認できる実名を送ってください。

**入力例**

```text
山田 太郎
```

### 5.2 過去に登録した人

```text
ガイド
  → 「LINEで本人ログイン」
  → ホームで実名を確認
  → 8/2が未登録なら「参加登録」
     またはスタッフLINEへ「イベント変更」と送信
  → ショートカットを確認／追加
  → デモを最後まで操作
  → 自分のスタッフLINEに2通届くことを確認
  → 準備完了
```

**ページ上の案内文**

> 過去に一度登録した方は、友だち追加やプロフィールの作り直しは不要です。本人ログイン後、今回のイベントが「登録済み」かだけ確認してください。

### 5.3 名前が違うとき

スタッフ用LINEへ、次の形式で送る。

```text
名前変更 山田 太郎
```

変更後、ホームを再読み込みしてスタッフ登録名を確認する。

### 5.4 セッション切れから戻る

```text
ホーム画面ショートカット
  → ログイン画面が表示
  → 「LINEで本人ログイン」
  → LINE認証
  → Safari／Chromeへ戻る
  → ホーム
```

スタッフ用LINEで `ヘルプ` と送ってログインURLを取り直す方法も併記する。

### 5.5 当日の現場フロー

```text
保護者がLINE受付・問診を完了
  → スタッフが来場者QRを読み取る
  → 氏名・問診を確認
  → 写真撮影と簡易検査を進める
  → AI分析を実行
  → レポート内容を確認
  → 保護者LINEへレポートを送信
  → 続けて相談・Instagram・相談用LINE案内が届く
  → 対応完了
```

- 展開中のブロックは濃色背景と枠線で強調し、同時に複数は開かない
- 詳細には説明、実行項目、実際の画面を縮小した端末イメージを表示する

### 6.4 必須の事前準備

診断の流れの直後に、独立した大きな作業ブロックを置く。

- 見出し: `アプリ登録を完了してください`

- 対象: 8/2に参加するスタッフ全員

- 選択後: `必須`、`事前準備 02`、`アプリ登録・動作確認`を表示
- 各手順は実行後にチェックし、全項目完了を準備完了条件とする

## 7. デバイス別ガイド

### 7.1 サポート方針

公開時点では未検証の最低OSバージョンを断定しない。次を「推奨環境」とし、実機試験後に確定する。

| 端末 | 推奨 | 実機試験対象 |
|---|---|---|
| iPhone | 最新版LINE、Safari、最新iOSまたは1世代前 | 最新iOS、1世代前のSafari |
| Android | 最新版LINE、Chrome、最新Androidまたは1世代前 | Pixel系、Galaxy系のChrome |
| 共通 | 通常タブ、カメラ許可、安定した通信 | LINE→外部ブラウザ、QR、写真、再ログイン、LINE着信 |

プライベートブラウズ／シークレットモードはセッション保持が不安定になるため非推奨とする。

### 7.2 iPhone

**外部ブラウザ**

1. LINEで本人ログインを開始する
2. 「Safariで開く」を押す
3. 自動で開かない場合は、LINEのメニューからブラウザで開く

**ホーム画面ショートカット**

1. Safari下部の共有ボタンを押す
2. 「ホーム画面に追加」を選ぶ
3. 名前を `cOral up` として追加する

**カメラを拒否した場合**

- SafariのWebサイト設定またはiPhoneの設定からカメラを許可する
- 許可後にページを再読み込みする

### 7.3 Android

**外部ブラウザ**

1. LINEで本人ログインを開始する
2. 「Chromeで開く」を押す
3. 自動で開かない場合は、LINEのメニューからデフォルトブラウザで開く

**ホーム画面ショートカット**

1. Chrome右上のメニューを押す
2. 「ホーム画面に追加」を選ぶ
3. 名前を `cOral up` として追加する

**カメラを拒否した場合**

- Chromeのサイト設定からカメラを許可する
- 許可後にページを再読み込みする

## 8. デモ仕様と準備完了チェック

### 8.1 デモで試すこと

1. デモ対象者の情報を確認する
2. 問診内容を見る
3. 写真・診断項目を一通り操作する
4. AI分析結果を見る
5. デモレポートを開く
6. LINE送信を実行する
7. 自分のスタッフ用LINEに次の2通が届くことを確認する
   - デモレポート通知
   - 個別相談、Instagram、相談用公式LINEの案内

### 8.2 デモの副作用

| 対象 | 挙動 |
|---|---|
| 問診・写真・分析・レポート | モック。デモ画面内で完結 |
| 本番visit、report | 更新しない |
| 本番来場者のLINE送信ログ | 更新しない。デモ本人送信用のスナップショットだけを`demo_report`として記録 |

## 9. トラブルシューターとFAQ

### 9.1 症状から解決する

FAQより先に、緊急度の高い症状をカードで並べる。

| 症状 | 最初に行うこと | 次の手段 |
|---|---|---|
| 「未登録です」と出る | 正しいスタッフ用LINEを追加し、実名登録を完了 | LIFFを開き直す |
| 「アカウント無効」と出る | スタッフ用LINEのブロックを解除し再追加 | 管理者にアカウント状態確認を依頼 |
| Safari／Chromeが開かない | 画面の「外部ブラウザで開く」を押す | LINEメニューからブラウザで開く |
| ブックマークからPIN画面になった | 「LINEで本人ログイン」を押す | スタッフLINEへ `ヘルプ` と送る |
| カメラが使えない | ブラウザのカメラ権限を許可し再読込 | LINE内ブラウザでないか確認 |
| QRが読めない | 明るさ、距離、画面反射を調整 | セッションIDの手動入力へ切替 |
| 8/2が登録済みでない | ホームの「参加登録」 | LINEへ `イベント変更` と送る |
| デモLINEが届かない | 友だち状態と本人LIFFログインを確認 | 再送後、管理者へ確認 |

### 9.2 FAQ本文

**Q. LINE名とスタッフ登録名は同じですか？**  
A. 同じとは限りません。アプリには、スタッフ用LINEで入力した実名を表示します。

**Q. 登録済みですが、名前が違います。**  
A. スタッフ用LINEへ `名前変更 山田 太郎` の形式で送ってください。

**Q. 過去に参加しました。もう一度登録が必要ですか？**  
A. プロフィールの再登録は不要です。LINEで本人ログインし、8/2イベントが登録済みか確認してください。

**Q. 過去のイベントと8/2の両方に参加できますか？**  
A. はい。同じスタッフに複数イベントを紐付けて管理します。今回の参加登録を追加しても、以前の登録は消えません。

**Q. 鹿児島など以前のイベントが表示されます。**  
A. 過去の参加情報です。8/2 YourTIME.8th 東京が「登録済み」なら問題ありません。ホームの標準一覧は開催中・開催予定を優先表示します。

**Q. 「未登録です」と表示されます。**  
A. `https://lin.ee/ZUvmToP` のスタッフ用LINEを友だち追加し、実名登録を完了してから本人ログインを開いてください。

**Q. 「アカウント無効」と表示されます。**  
A. スタッフ用LINEのブロック解除・再友だち追加を試してください。解消しない場合は、管理者による状態確認が必要です。

**Q. Safari／Chromeが自動で開きません。**  
A. 画面の「外部ブラウザで開く」を押してください。それでも開かない場合は、LINEのメニューからデフォルトブラウザで開きます。

**Q. ブックマークから開いたらログイン画面になりました。**  
A. セッションは最大7日で切れることがあります。「LINEで本人ログイン」から認証し直してください。

**Q. カメラが使えません。**  
A. SafariまたはChromeのカメラ権限を許可し、ページを再読み込みしてください。LINE内ブラウザは使いません。

**Q. QRが読めません。**  
A. QRの明るさ、端末との距離、画面反射を調整してください。改善しない場合はセッションIDを手動入力します。

**Q. デモLINEが届きません。**  
A. スタッフ用LINEが友だち状態か、本人としてLIFFログインしているかを確認してください。

**Q. デモ操作は本番データへ保存されますか？**  
A. 保存されません。ログイン中のスタッフ本人へのLINE送信だけ実行されます。

**Q. 1台の端末を複数人で共有できますか？**  
A. 可能ですが、利用後に必ずログアウトしてください。本人セッションは最大7日残ります。

## 12. モーション設計とOSS選定

### 12.1 原則

- 動きは「現在地」「次の操作」「完了」を理解させるために使う
- 180〜450ms、総スタッガー400ms以内
- `opacity` と `transform` を中心にし、レイアウトシフトを起こさない
- モバイルで常時動く要素は最大3つ
- `prefers-reduced-motion` に対応し、動きを切っても情報が欠落しない
- 自動カルーセル、追従カーソル、スクロールジャックは使わない

### 12.2 採用する演出

| 場所 | 演出 | 目的 |
|---|---|---|
| Hero | 見出しの60ms文字列スタッガー、低速の水中光 | ブランドへの没入 |
| ページ上端 | 細いスクロール進捗 | ページ量と現在地の把握 |
| 当日フロー | 12px下から一度だけ現れる | 手順の順序を理解 |
| 登録分岐 | タブ下線とカードの滑らかな切替 | 新規／既存を迷わせない |
| 外部ブラウザ | ボタン操作でLINE→ブラウザのミニデモ | 操作を言葉だけにしない |
| チェックリスト | チェックと進捗リング | 完了感を与える |
| FAQ | 高さと透明度のアコーディオン | 文量を抑える |
| 最終CTA | 1回だけの淡い光 | 次の行動を示す |

### 12.3 OSS判断

既存の `framer-motion@^11.18.2` とCSSで実現し、新規依存は追加しない。

| 候補 | 判断 | 理由 |
|---|---|---|
| Framer Motion / Motion | 採用 | 既に導入済み。React統合、reduced motion、遅延読込が可能 |
| Motion Primitives | 参照のみ | 良質な実装例だが、ベータ依存を増やす必要はない |
| GSAP | 不採用 | 今回の演出には過剰。追加のライセンス・運用判断を増やす |
| Lenis | 不採用 | スクロール挙動を変更し、現場ページの操作性を下げる |
| React Three Fiber | 不採用 | 端末負荷、バンドル、保守コストが目的に合わない |
| React Bits | 参照のみ | 表現参考にはなるが、ライセンス条件確認と品質統一が必要 |

`MotionConfig reducedMotion="user"` とCSSの `prefers-reduced-motion` を併用する。ページ本体はServer Componentとし、タブ、デモ、チェック、FAQだけをClient Componentにする。

## 14. 非機能要件

### 14.1 アクセシビリティ

- WCAG 2.2 AA相当を目標にする
- 文字と背景は十分なコントラストを確保する
- 全操作をキーボードで実行できる
- フォーカスリングを消さない
- アコーディオンには `aria-expanded` と関連付けを持たせる
- 色だけで完了・エラーを表さない
- 動画や自動アニメーションに依存しない
- 200%拡大時にも横スクロールを発生させない

### 14.2 性能

- モバイル4G相当で主要見出しと開始CTAを先に表示する
- LCP 2.5秒未満、CLS 0.1未満、INP 200ms未満を目標とする
- Hero画像はAVIF/WebPと適切な `sizes` を用い、装飾SVGは軽量化する
- ページ固有Client JavaScriptは必要な島だけへ限定する
- 下部のデバイスデモなどは遅延読込する
- フォント読込中も本文が読めるフォールバックを設定する

### 14.3 セキュリティ・プライバシー

- 公開ガイドは個人情報を表示・収集しない
- localStorageへ実名や認証情報を保存しない
- 認証Cookieの詳細値を画面やログに出さない
- デモ送信は必ずログイン中スタッフ本人へ限定する
- 端末共有時のログアウトを案内する
- 共通PINをHTML、JavaScript、OGP、資料へ含めない

### 14.4 可用性

- JavaScriptが一時的に失敗しても、手順本文とリンクは読める
- アニメーションが失敗してもCTAは常に操作できる
- LINE自動遷移が失敗しても手動ボタンを残す
- ネットワーク失敗時は再試行と問い合わせの両方を提示する

## 16. イベント識別のDB・レポート設計

### 16.1 結論

スタッフの参加イベント登録は必要であり、文字列タグをプロフィールへ追加するのではなく、現在の `event_staffs` 中間テーブルで管理する。この方式なら、同じ人が鹿児島、東京など複数イベントへ参加してもプロフィールを重複作成せずに済む。

ただし、`event_staffs` は「そのスタッフがどのイベントへ参加予定か」を表す。来場者の診断データがどのイベントで作られたかは、必ず `visits.event_id` で管理する。両者を混同しない。

```text
profiles ──< event_staffs >── events
   │                              │
   └──────── staff_profile_id     │ event_id
                    visits >──────┘
                       │
                       ├── diagnoses
                       ├── reports
                       ├── visit_photos
                       └── line_message_logs
```

| 情報 | 正本 | 意味 |
|---|---|---|
| スタッフの参加予定 | `event_staffs(event_id, profile_id)` | 誰がどのイベントに参加するか |
| 来場・診断の開催イベント | `visits.event_id` | その来場データがどのイベントのものか |
| 担当したスタッフ | `visits.staff_profile_id` | 実際に誰が対応したか |
| レポートのイベント | `reports.visit_id → visits.event_id` | レポート元来場のイベント |
| LINE送信のイベント | `line_message_logs.visit_id → visits.event_id` | どのイベントの送信か |

### 16.2 8/2イベントマスター

`events` の正本値は次とする。

| カラム | 値 |
|---|---|
| `event_id` | `yourtime-8th-tokyo-2026` |
| `name` | `8/2 YourTIME.8th 東京` |
| `start_date` | `2026-08-02T10:30:00+09:00` |
| `end_date` | `2026-08-02T16:30:00+09:00` |
| `venue` | `東京流通センター 第1展示場C・D（東京都大田区平和島6-1-1）` |
| `status` | `upcoming`。当日は `active`、終了後は `completed` |

人が読む安定コードは `events.event_id`、リレーションには `events.id` のUUIDを使う。

### 16.3 来場データへのイベント伝播

`DEFAULT_EVENT_ID` の暗黙設定だけに依存しない。保護者のイベント入口に安定コードを含め、サーバーでUUIDへ解決してvisitへ保存する。

```text
8/2専用LINE／QR／LIFF入口
  ?event=yourtime-8th-tokyo-2026
        ↓ サーバーでeventsを検索・status検証
events.id（UUID）
        ↓
visits.event_id
        ↓
診断・写真・レポート・LINE送信
```

**入力境界**

- クライアントから受け取ったUUIDやイベント名をそのまま信用しない
- 安定コードをサーバーで `events` に照合し、存在、開催状態、開催期間を検証する
- 解決できなければvisitをイベントなしで作らず、明確なエラーと再試行導線を返す
- 既存の進行中visitを再利用する場合も、8/2入口から別イベントのvisitを誤って再利用しない
- `DEFAULT_EVENT_ID` は緊急時の環境フォールバックに限定し、起動時またはヘルスチェックで実在イベントと一致するか検証する

### 16.4 レポートへの表示

保護者が後から見ても開催元が分かるよう、次の3か所へ同じイベント名を表示する。

1. スタッフのレポート確認画面
2. 保護者向けWebレポートのヘッダー
3. LINEのレポート通知Flex Message

表示は次へ統一する。

```text
8/2 YourTIME.8th 東京
2026年8月2日　東京流通センター 第1展示場C・D
```

イベント名はクライアントから任意指定せず、LINE送信時に `visitId` からサーバー側で `visits → events` をJOINして取得する。現在の `eventName?: string` は表示用の外部入力ではなく、サーバー内部で解決した値だけをメッセージ生成器へ渡す。

### 16.5 履歴の不変性

正規化された正本は `visits.event_id → events` とする。イベント終了後に名前・会場を上書きしない運用を必須とする。

将来イベント情報の編集履歴が必要になった場合は、レポート生成時の `event_name`、開催日、会場を `reports.event_snapshot` に保存する。8/2前は新規カラムを必須にせず、イベントマスターを不変データとして扱い、不要な本番スキーマ変更を増やさない。

### 16.6 管理・集計で可能になること

- 8/2参加予定スタッフ一覧: `event_staffs → profiles`
- 8/2の来場数・完了数・LINE送信数: `visits` を `event_id` で集計
- スタッフ別対応件数: `visits(event_id, staff_profile_id)` で集計
- 送信失敗一覧: `line_message_logs → visits.event_id` で抽出
- 同一スタッフのイベント参加履歴: `profiles → event_staffs → events`

スタッフの参加登録を、来場データのイベント判定に流用しない。複数イベントへ登録済みのスタッフがいても、来場者の入口とvisitがイベントを一意に決める。

## 18. 無説明運用のユーザビリティ試験

### 18.1 合格判定

制作者や運営者が横から教えない状態で、対象スタッフによる実地試験を行う。画面投影による事前説明を合格条件に含めない。

最低5名で実施し、次を満たしたときだけ「説明なしで運用可能」と判定する。

- 初参加者3名中3名が、質問なしで登録、外部ブラウザ、ショートカット、デモLINE着信まで完了する
- 既存スタッフ2名中2名が、プロフィールを再作成せず8/2登録状態を確認する
- 全員が、ホームに表示された実名とイベント名を声に出して正しく説明できる
- 全員が、当日クイックモードから診断開始とカメラ復旧手順を見つけられる
- 重大な迷い、行き止まり、誤ったイベント登録が0件
- 新規スタッフは5分以内、既存スタッフは2分以内を目安に準備経路へ到達する

試験中、運営者は操作を教えず、詰まった画面、発言、所要時間だけを記録する。1人でも重大箇所で止まった場合は、その人へ追加説明するのではなくページまたはアプリを修正して再試験する。

### 18.2 投影説明の位置付け

画面投影や口頭説明は、チームの目的共有や安心感づくりには使ってよい。しかし、登録・ログイン・端末設定を成立させる必須工程にはしない。

運営者が説明会で見せる場合も、ガイドページを上から読み上げるのではなく、次の3点だけを共有する。

1. 何のためのアプリか
2. 当日の来場者体験
3. 各自が準備完了証まで終えること

具体的な端末操作は、各スタッフが自分の端末でガイドに沿って完了する。

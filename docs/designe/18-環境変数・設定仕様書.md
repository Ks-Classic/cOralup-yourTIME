## 1. 環境変数一覧

## 4. セキュリティ注意事項

### 公開可能（`NEXT_PUBLIC_` prefix）
- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `NEXT_PUBLIC_APP_URL`

### 秘密（サーバーサイドのみ）
- `SUPABASE_SERVICE_ROLE_KEY` - RLSをバイパスできる強力なキー
- `LINE_CHANNEL_SECRET` - Webhook署名検証用
- `LINE_MESSAGING_CHANNEL_ACCESS_TOKEN` - メッセージ送信用
- `GOOGLE_AI_API_KEY` - AI API呼び出し用
- `STAFF_PIN_CODE` - スタッフ認証用
- `LARK_APP_SECRET` - Lark API認証用
- `ADMIN_API_KEY` - 管理画面API認証用（サーバー側検証）

### ⚠️ 重要: クライアントにAPIキーを露出させない

以前は `NEXT_PUBLIC_ADMIN_API_KEY` を使用していましたが、**セキュリティ上の問題**があるため廃止しました。

```typescript
// ❌ NG: クライアントにAPIキーを露出
const adminApiKey = process.env.NEXT_PUBLIC_ADMIN_API_KEY
fetch('/api/admin/schemas', {
  headers: { Authorization: `Bearer ${adminApiKey}` }
})

// ✅ OK: 現在の暫定対応（認証なしでアクセス）
fetch('/api/admin/schemas')

// ✅ 将来: ログイン機能でセッションベース認証
```

## 6. アカウント移行計画

### 開発フェーズ（現在）
**個人アカウントで各サービスを作成して開発を進める**

| サービス | アカウント | 用途 |
|---------|-----------|------|
| Supabase | 個人アカウント | 開発・テスト用プロジェクト |
| LINE | 個人アカウント | 開発用チャネル（テスト用） |
| Google AI | 個人アカウント | 開発用APIキー |
| Vercel | 個人アカウント | 開発用デプロイ |
| GitHub | 個人アカウント | コード管理 |

### 本番移行（12/15頃）
**cOralupドメインアカウント取得後、本番環境に移行**

#### 移行可能なサービス
- **Supabase**: Organizationに移行（Export → Import）
- **Google AI**: APIキー再発行
- **Vercel**: Team移行
- **GitHub**: Organization移行

#### LINE（本番用は新規作成が必要）
- **移行不可**: プロバイダー・チャネルは個人アカウントから移行できない
- **対応**: cOralupアカウントで本番チャネルを新規作成
- **開発用チャネル**: テスト用として残しておく

#### 移行時の注意事項
1. **環境変数の分離**: 開発用（`.env.local`）と本番用（Vercel環境変数）を分けて管理
2. **Webhook URL**: 開発用と本番用で異なるURLが必要（両方のチャネルに設定）
3. **データ移行**: SupabaseはExport/Importでデータを移行可能
4. **LINE友だち数**: 本番チャネルは新規作成のため、友だち数は0から開始

## 7. RLS・APIアクセス方針

### 7.1 Supabase RLS (Row Level Security)

全テーブルでRLSをONにし、**service_role**のみフルアクセスを許可しています。

```sql
-- 全テーブルに適用
ALTER TABLE <table_name> ENABLE ROW LEVEL SECURITY;
CREATE POLICY "<table>_service_role_all" ON public.<table_name>
  FOR ALL TO service_role USING (true) WITH CHECK (true);
```

### 7.2 APIアクセスパターン

| 用途 | クライアント | 認証方式 | Supabaseキー |
|------|-------------|----------|--------------|
| **管理画面API** (`/api/admin/*`) | 管理UI | 暫定: なし（将来: ログイン） | Service Role |
| **本番問診/診断/LINE連携** (`/api/questionnaire/*`, `/api/diagnoses/*`, `/api/line/*` 等) | 保護者/スタッフUI | キー不要（サーバー内部処理） | Service Role |
| **公開読み取り** (将来的にViewで公開する場合) | 任意 | 不要 | Anon (RLS許可時のみ) |

### 7.3 詳細

#### 管理画面API（スキーマエディタ等）

**現在の暫定対応:**
- 認証ヘッダーなしでもアクセス可能
- 管理画面URLを知っている人のみアクセス可能な状態

```typescript
// サーバー側（API Route）- 暫定対応
const assertAdminAuthorized = (request: NextRequest) => {
  if (!adminApiKey) return // ADMIN_API_KEY未設定時は認証スキップ
  
  const authHeader = request.headers.get('authorization') || ''
  const bearer = authHeader.startsWith('Bearer ') ? authHeader.slice(7) : null
  const headerKey = request.headers.get('x-admin-key')
  
  // ヘッダーがない場合も許可（暫定対応）
  if (!bearer && !headerKey) return
  
  if (bearer === adminApiKey || headerKey === adminApiKey) return
  throw new Error('unauthorized')
}
```

```typescript
// クライアント側（管理UI）- 認証ヘッダーなし
const res = await fetch('/api/admin/schemas')
```

**将来の対応:**
- ログイン機能を実装
- セッションCookieベースで認証
- 管理者ユーザーのみアクセス可能

#### 本番問診/診断/LINE連携API
- クライアント（保護者/スタッフUI）はAPIキー不要でfetch
- サーバー側で Service Role クライアントを使用してDB操作
- セッションIDや訪問IDで対象データを特定（アプリレベルの認可）

```typescript
// サーバー側（API Route）
const supabase = createClient(url, process.env.SUPABASE_SERVICE_ROLE_KEY!)
const { data } = await supabase.from('sessions').select('*').eq('session_id', sessionId)
```

```typescript
// クライアント側（保護者/スタッフUI）
const res = await fetch(`/api/sessions?sessionId=${sessionId}`)
```

### 7.4 セキュリティ上の注意

1. **Anon Key はクライアントに公開しても安全**だが、RLS ON + ポリシーなしの状態では何もできない
2. **Service Role Key は絶対に公開しない**（サーバー環境変数のみ）
3. **ADMIN_API_KEY** は現在暫定対応で認証緩和中。将来的にはログイン機能で保護
4. 将来的に細かいRLSポリシー（例: `auth.uid()` ベース）を追加する場合は、Supabase Authを導入

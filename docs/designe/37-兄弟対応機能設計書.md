# 兄弟対応機能設計書

**作成日: 2025-12-16**
**ステータス: 設計完了 → 実装中**

---

## 1. 概要

### 1.1 背景・課題

イベント診断において、**兄弟で来場する家族**への対応が必要となった。

現状の課題:
- 1人の親御さん（LINE登録者）で複数の子供がいる場合の対応フローが未整備
- API実装が「1人の子供」を前提としている
- 兄弟を同時に別々のブースで診断させたい場合のワークフロー不在

### 1.2 目的

- 1人の親御さんが**複数の子供分の問診を入力**できるようにする
- **各子供ごとに個別のQRコード**を発行し、別々に診断可能にする
- 問診・診断結果を**子供単位で保存・管理**できるようにする

---

## 2. 現状分析

### 2.1 DB設計の確認結果

**結論: DB設計は既に兄弟対応済み** ✅

```
profiles (親)     →  1:N  →    children (子)
    │                               │
    └───────────────────────────────┼────────→ visits (診断セッション)
                                    │
                               child_id で紐付け
```

| テーブル | 構造 | 兄弟対応 |
|---------|------|---------|
| `profiles` | 親御さん情報（LINE ID含む） | ✅ 問題なし |
| `children` | 子供情報（`parent_profile_id` で親に紐付く） | ✅ **1:N対応済み** |
| `visits` | 診断セッション（`child_id` で子供に紐付く） | ✅ **1:N対応済み** |

### 2.2 API実装の問題点

| ファイル | 問題 | 修正内容 |
|---------|------|---------|
| `/api/parent/basic-info` | `.single()` で1件のみ取得 | 複数対応に修正 |
| `/api/parent/visit` | `.limit(1)` で1件のみ取得 | 全子供を返すように修正 |

## 3. 設計方針

### 3.1 アプローチ

**ハイブリッド方式**を採用:

1. **子供選択ステップの追加**: 問診開始時に「どの子の問診？」を選択
2. **問診完了時の分岐**: 「もう1人追加」ボタンで繰り返し
3. **既存フローの維持**: 初回利用者は従来通り基本情報入力から開始

### 3.2 フロー設計


## 5. API設計

### 5.1 既存API修正

#### GET `/api/parent/visit`

**変更内容**: 全ての子供と各子供のvisitを返すように修正

```typescript
// Before
.limit(1)

// After
// 全ての子供を取得（limit削除）
const { data: children } = await supabase
  .from('children')
  .select(`
    id, first_name, last_name, birthday, gender,
    visits (
      id, status, session_id, visit_date, child_age_months
    )
  `)
  .eq('parent_profile_id', profile.id)
  .order('birthday', { ascending: false })
```

**レスポンス変更**:

```typescript
// Before
{
  profile: {...},
  child: {...} | null,
  visit: {...} | null,
  questionnaireResponses: [...]
}

// After
{
  profile: {...},
  children: [
    {
      id, firstName, lastName, birthday, gender,
      visits: [
        { id, status, sessionId, visitDate, childAgeMonths }
      ]
    },
    ...
  ],
  // 後方互換のため残す
  child: {...} | null,  // 最新の子供
  visit: {...} | null,  // 最新のvisit
}
```

#### POST `/api/parent/basic-info`

**変更内容**: `childId` パラメータ対応

```typescript
interface BasicInfoRequest {
  lineUserId: string
  childId?: string  // 既存の子供を更新する場合
  // ... 既存パラメータ
}

// childIdがある → 既存子供を更新
// childIdがない → 新規子供を作成
```

### 5.2 新規API（不要）

DB設計が既に対応済みのため、新規APIは不要。

## 7. データフロー

### 7.1 兄弟2人分の問診入力

```
時間軸 →

親御さん操作                      DB状態
─────────────────────────────────────────────────────

(1) LINE友だち登録
                                  profiles: P001 (田中太郎)

(2) 問診開始（1人目）
    基本情報入力: はるき           children: C001 (はるき) → P001
                                  visits: V001 → C001, status=in_progress

(3) 詳細問診入力
    問診回答保存                   questionnaire_responses: V001に紐付く
                                  visits: V001, status=completed

(4) QRコード表示
    「もう1人追加」クリック

(5) 子供選択画面
    「新しい子を追加」クリック

(6) 基本情報入力: ゆうな
                                  children: C002 (ゆうな) → P001
                                  visits: V002 → C002, status=in_progress

(7) 詳細問診入力
    問診回答保存                   questionnaire_responses: V002に紐付く
                                  visits: V002, status=completed

(8) QRコード表示
    2人分のQRコード準備完了
```

### 7.2 スタッフ側のフロー（変更なし）

スタッフはQRコードをスキャンするだけ。
各QRコードは異なる `session_id` を持つため、兄弟それぞれを独立して診断できる。

```
スタッフA: QRスキャン（V001）→ はるきの診断
スタッフB: QRスキャン（V002）→ ゆうなの診断（同時並行可能）
```
